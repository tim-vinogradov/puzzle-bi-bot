# Архитектура Puzzle BI-бота

## Поток обработки сообщения

1. **Понимание** (`app/nlu`). Сообщение превращается в список *действий* — JSON-объектов вида
   `{"type": "add_calc", "calcs": [{"kind": "expr", "expr": "fact / plan * 100"}]}`.
   - `rules.py` — детерминированный разборщик русского языка: периоды («за последний квартал», «2 квартал 2026», «с марта по август 2025»), разрезы («по регионам и торговым точкам»), сущности (регионы в любых падежах, категории, 42 продукта, 61 город, клиенты с нечётким поиском), вычисления, команды дашборда. Составные фразы («добавь колонку … и перестрой третий график») делятся на несколько действий.
   - `llm.py` — языковая модель (OpenAI-совместимый API или GigaChat) получает системный промпт со схемой данных, справочниками и текущим состоянием дашборда и возвращает тот же JSON.
   - `actions.py` — белый список типов и полей. Всё лишнее отбрасывается до выполнения.
   - Режим `hybrid`: уверенные совпадения правил выполняются сразу (быстро, бесплатно, воспроизводимо), неуверенные уходят в модель; при недоступности модели — правила.

2. **Данные** (`semantic.py`, `db.py`, `sql_guard.py`).
   - Семантический слой описывает три набора: *Продажи: план и факт* (месяц × точка × продукт), *Скидки* (месяц × клиент × продукт × причина), *Продажи по клиентам*.
   - Конструктор собирает SQL под диалект (PostgreSQL / SQLite): план и факт объединяются через `UNION ALL` по ключу месяц-точка-продукт, так что строки «план есть, продаж нет» и наоборот не теряются.
   - Вместе с таблицей выгружается тот же период годом ранее (для динамики к прошлому году) и связи «точка-продукт-клиент» (для подсчёта активных клиентов под любыми фильтрами).
   - Любой SQL (и свой, и от модели) проходит `validate_select`: разбор sqlglot, ровно один SELECT, только таблицы кейса, запрет системных схем и опасных функций, лимит строк. Подключение — роль только для чтения / SQLite `mode=ro`, `statement_timeout` / прерывание по таймеру.

3. **Вычисления** (`calc.py`). Вычисление хранится как описание, а не как код:
   `expr` (формула), `share` (доля), `change` (динамика м/м, г/г), `cumsum`, `rank`, `group_stat`.
   - Формулы разбираются `ast` по белому списку: числа, колонки, `+ − × ÷`, скобки, `abs`, `round`. Деление на ноль → пусто, а не ошибка.
   - Каждое вычисление умеет считаться на уровне строк таблицы (`materialize`) и на уровне агрегации графика (`aggregate`). Отношения пересчитываются из сумм — «% выполнения по региону» = факт региона / план региона, а не среднее процентов.
   - Динамика к предыдущему месяцу для первого месяца периода берёт значение из выгруженного прошлогоднего периода.
   - Вычисление выполняется с таймаутом.

4. **Дашборд** (`dashboard.py`, `charts.py`). Состояние = метаданные (запрос, период, графики, вычисления, фильтры, переключатели, история) + ссылки на неизменяемые таблицы. Отрисовка: фильтрация → KPI → 1–6 графиков Plotly → резюме. Графики строятся на сервере в JSON и рисуются plotly.js в браузере.
   - Единый стиль: палитра проверена на различимость при дальтонизме, план — серый, факт — синий, статусы — зелёный/красный всегда с подписью в легенде.
   - Цвет закреплён за сущностью: регион «Центральный» одного цвета на всех графиках и при любых фильтрах.
   - Пустые данные → аккуратная надпись «Нет данных для выбранных фильтров», а не ошибка.

5. **Хранилище** (`storage.py`) — отдельная SQLite `storage/app.db` (база с данными остаётся только для чтения):
   `dashboards` (название, запрос, описание, даты, токен ссылки, мягкое удаление), `versions` (каждое сохранение — новая версия), `blobs` (сжатые таблицы, дедупликация по хешу), `sessions` (переписка и автосохранённый черновик).

6. **Интерфейс** (`static/`) — без сборки. Чат, блоки ответа (текст, SQL, таблица с сортировкой/страницами/группировкой, дашборд, список, уточнение с кнопками, файл, история версий), Tom Select для фильтров с поиском, синхронный зум, PNG всего дашборда (сборка на canvas), режим «по ссылке».

## Почему так

- **Единая плоская таблица** — все графики и KPI строятся из неё, поэтому вычисления, фильтры и переключатели автоматически действуют на всё.
- **Действия вместо кода** — модель не может «сделать лишнее»: её ответ — данные, которые проверяются.
- **Правила + модель** — демо и типовые вопросы работают мгновенно и без внешних сервисов; модель подключается для свободных формулировок и произвольных SELECT.

## Соответствие требованиям кейса

| Требование | Где |
|---|---|
| Вопрос на естественном языке, бот понимает, что нужна визуализация | `nlu/rules.py`, `nlu/llm.py`, `bot.do_build` |
| Бот сам достаёт данные из базы | `semantic.build_sql`, `db.run_select` |
| Единая таблица показывается пользователю | блок `table` после каждого запроса, «Покажи таблицу» |
| Вычисления словами, колонками, пересчёт графиков | `calc.py`, `bot.do_add_calc`, `bot.do_rebuild_chart` |
| 4 графика, единый стиль, общие оси, согласованные цвета | `charts.py`, синхронный зум в `app.js` |
| Фильтры с поиском, мультивыбор, каскад, на все графики и KPI | `dashboard.filter_panel`, Tom Select |
| Переключатели разреза, метрики, периода, вида | `dashboard.switch_panel` |
| KPI сверху, зелёный/красный | `dashboard.compute_kpis` |
| Уточнения, резюме | `bot.do_build` (clarify), `dashboard.summarize` |
| Сохранение, список, поиск, сортировка, открытие, переименование, копия, удаление | `storage.py`, `bot.do_*` |
| История версий, черновик, выгрузка, ссылка, шаблоны | `storage.versions`, `sessions`, `export.py`, `/share/…`, «стандартный дашборд» |
| Безопасность, таймауты, пустые данные | `sql_guard.py`, `db.py`, `calc.py`, `charts.empty_figure` |
